分享一种与 Agent 共建的思维方法，帮助你从一个看不清全貌的想法出发，构建出一份任何智能体都能接手的 MVP 方案。
某天晚上我在跟 Claude Code 聊一个想法。
我手上维护了好几个软件服务，比如订单服务、充值服务，分散在一堆服务器上，每天排查问题都得连内网，登堡垒机、在机器 grep 日志，由于没有日志中心采集服务，导致每次查日志很耗时。我冒出来一个念头，能不能做个 MCP，我直接说一句「某某单号卡单了帮我看看」，它就自动把日志给我捞出来。
这个想法很粗糙。
我自己也说不清它该怎么设计。用什么语言写 MCP？每个服务的日志格式都不一样怎么办？服务在内网怎么穿透？
但我没直接让它给我写代码（虽然现在写代码真的很快了），我跟它说了六个字。
先扩散，后收敛。
然后我们就开始聊。大概一个多小时之后，我得到了一份一万多字的实施方案，架构分层、技术选型、目录结构、完整代码骨架、MCP 调用的 token 怎么签发、日志路径差异怎么处理...等等，非常之详细。详细到每一个技术决策背后是如何决定的，都有其背景和分析。
所以，本文想分享的是「先扩散后收敛」这六个字本身，这是一种和 Agent 共建的思维方式。
于是就有了今天这篇文章，和这个 skill。
实施方案
01扩散和收敛
我先说说这玩意是个啥，其实特别简单，就两个动作，一前一后。
第一个动作，扩散。
一个不成熟的想法，我自己往往是看不清它全貌的，我以为我要做的是 A，但 A 背后牵扯着 B、C、D，还有我压根没想到的 E。扩散就是让 AI 帮我把这张地图铺开，把我不知道的、可能相关的、还有那些看着像一行字不起眼，其实会改写整个设计的暗礁（隐性缺陷），全部都列出来。
第二个动作，收敛。
地图铺开了，路就有好几条，收敛就是顺着我感兴趣的方向往下钻，每聊清楚一个分叉，就锁死一个决策，把不确定的内容变成可以实施的方案。
比如让 Agent 查询内网服务器日志，使用 SSH 直连还是服务器侧单独部署一个 agent 配合 MCP 服务调用？当我决定使服务器侧 agent 时，那么 agent 用 Python 还是 Java？决定锁定 Python，因为真正干活的是 grep 命令（查询日志），agent 只是个壳，内存比 Java 能省到 20MB。那么多服务上报要不要注册中心呢？至少 MVP 版本不要，直接静态配置服务器地址，先跑起来再说。
就这么一个一个锁，锁到最后，所有问题都解决完了，一条能走通的完整路径自己就浮出来了，这就是我要的 MVP 方案。
扩散追的是广度，把我不知道的呈现上来，而收敛追的是确定性，把模糊的确定下来。一散一收，一个完整的方案就从一个不完整的想法中孵化出来。
就这么简单，事实上，除了用它构建软件方案非常好用之外，金融、社科、市场营销方案一样适用。
02双钻模型
其实这套东西不是我凭空想的。
设计领域有个特别经典的模型，叫双钻模型(Double Diamond，英国设计协会提出的设计流程框架)。第一颗钻石负责发现问题，先发散再收敛，搞清楚真正要解决的是什么；第二颗钻石负责解决问题，再发散再收敛，找出怎么解。
心理学里也早有这个区分。吉尔福特(J.P. Guilford，提出智力结构理论的美国心理学家) 把人的思维分成发散思维和收敛思维，发散是从一个点生出无数可能，收敛是从无数可能里逼近一个答案。创造力强的人，这两种思维都强、而且能自由切换。
我做的「扩散收敛法.skill」就是把这些前人早就验证过的东西抽出来，配上 Agent 语义，做成一套通用的 Skill。
以前一个人发散，受限于自己的知识边界，不知道的就是不知道。现在扩散这一步 AI 能帮我把认知盲区里的东西捞出来，相当于给发散装了个专家外挂。而收敛这一步，因为是我在选方向和定决策，所以最后这份方案还是基于我的工程经验创造出来的。我也一直强调，我们永远不要丢掉自己的判断力。
03完美的对话
用上这个 Skill 后每一轮 AI 的回答，我希望它最好都带这么几样东西。
首先重要的判断要带上置信度，比如「这个我建议用方案 B，置信度大概 85%」，我好知道哪些是它有把握的、哪些是它也在猜测。
每个决策点的分叉（对比方案）用表格列对比，两三个方案摆一起，优劣对比，最优推荐的那个放第一个并标出来。
其次，要求 AI 每一轮只问我一个问题，不是甩给我十个问题让我挑，那一个问题就是最关键分叉（基础变量），它决定着底下的所有设计，我答完后，才能继续下一轮扩散。
整个过程就是 AI 和我来回拉扯和共建，它负责铺地图、我选方向、然后再铺下一层，直到 MVP 版本做完。
最后，当所有决策都锁完了，我会跟它说一句:
「我们对话至此，你已经完全地知道我所想的内容，通过扩散和收敛，你也清楚了具体的实施步骤了，包含框架、细节、注意事项，以及上下文的所有内容，请将其保存到本地一个完整的实施步骤文档。要求详细，不要遗漏以上我们所有共同探索出的所有内容。」
输出方案
这句话是整个方法的收口，它会把这一个多小时聊出来的所有东西，每个决策、每条依据、每个被否决的方案和否决的理由、每个留给未来的口子，全部汇总成一份手稿。
这份手稿是干嘛用的呢？它是我跟下一个 Agent 协作的起点。
打个比方，我跟一个领域专家深聊了一下午，最后他给我一份纪要。这份纪要拿出去，无论是我自己照着做，还是丢给另一个 AI 让它接着干，对方都不用再从零开始问我到底想要啥，因为想清楚的过程，全在这份手稿里了，这就是最终的 MVP 版本方案。
04扩散收敛法 Skill
这套方法跟软件本身一点关系都没有，它本质上是一套面对任何陌生复杂问题时的提问框架，完整的思维结构。
如果你是一个研究生，做一个研究课题，扩散能铺开相关文献、对立假设、方法论选项，收敛帮着锁定研究问题和范围。
如果你是一个创业者，做一个商业决策，扩散能看清市场、竞品、风险、资源约束，收敛帮着定方向、分资源、排里程碑。
写一篇文章、设计一个产品、甚至规划自己接下来三年怎么走，本质上都是一回事，构建和创造。
如果你想构建的内容没有标准答案，一开始看不清全貌，它就非常适用，唯一的变量只是地图上的内容不同罢了。
当然，它也不是万能的。
它替代不了我的判断力，它能在很短时间内把一个完整的框架搭起来，但框架不等于落地，那份最终的方案只是起点，不是终点。
我现在的用法是，先用它把框架快速搭起来，然后挑那些我存疑的、或者特别关键的点，自己再深入去验证、去抠细节。AI 搭框架加我抠细节，这个组合比我从零开始硬写，效率高太多了。
这个方法我把它做成了一个 skill，叫 diverge-converge(扩散收敛法)。详细地址：https://github.com/linshidream/skill-hub
## 这个 skill 是什么

它定义的是**协议**，不是脚本：当用户带着一个不成熟的想法来，这个 skill 规定 agent 如何扮演思维合伙人，通过受控的扩散与收敛，把模糊想法逼近成完整可实施方案，最后结晶为手稿。

核心交付不是任何单轮回答，而是**累积锁定的决策 + 其依据 + 被否决的备选**——最终沉淀为一份手稿，成为后续与其他 agent 协作的工作基础。

## 为什么是"先扩散，后收敛"

一个不成熟的想法有**隐藏的完整形状**。想法的主人看不见它，因为缺少地图。

- **若不先扩散就收敛**：你在看不见地形时就承诺了一条路，只能做局部优化，等撞上承重约束时已经太晚、改动成本已经很高。(典型：软件里的时区暗礁、研究里被忽略的混杂变量、创业里没算到的现金流回款周期——这些都是"以为是一行字"、实则改写整个方案的点，只有扩散才能在便宜的时候暴露它们。)
- **扩散的职责**：把用户不知道的点、可能相关的点铺开，扩张地图，暴露未知的未知 (unknown-unknowns)。
- **收敛的职责**：每次锁定一个决策，直到所有问题都解决完，一条可走通的完整路径浮现——MVP 方案就有了。

扩散与收敛**不是两个阶段，是一台双相引擎**。每一轮对话都可能既扩张某个子领域、又锁死一个决策。随着轮次推进，重心从"以扩散为主"平滑滑向"以收敛为主"。

## 使用场景(触发信号)

- 用户带着半成熟想法，说"先扩散后收敛"、"扩散收敛一下"、"diverge-converge"、"帮我把这个想法展开"
- 用户想在动手前"看清这件事的全貌"、"有哪些我没考虑到的点"
- 用户想把一段多轮探讨/头脑风暴**结晶成一份可实施文档/会议纪要/手稿**
- 任何复杂、开放、没有现成答案的课题：软件架构、研究选题、商业决策、产品设计、政策制定、写作框架、职业规划……这个 Skill 就是把上面这一整套对话协议写进规则里，比如怎么听懂我的想法、怎么扩散、怎么每轮只问一个问题、怎么维护那个决策台账、怎么判断闭合、最后怎么形成成手稿。
装上之后，带着一个还没想清楚的想法去找它，说一句「我有个想法，先扩散后收敛」，它就会进入思维合伙人的模式，陪着一轮一轮把想法聊清楚。最后说一句「形成可实施文档」，它就把整段对话结晶成手稿。
skill 的结构就四步:
读懂想法 → [扩散 ↔ 选方向深入 ↔ 收敛](循环，重心慢慢从扩散滑向收敛) → 检测闭合 → 形成手稿放到 ~/skills/ 目录下就能用。
05写在最后
我本身就是软件工程师，我的工程思维可以用在其他的行业上，扩散收敛法就是我日常工作中的思考模型，它用于处理任何复杂的事情。
当机械代替体力，AI 代替智力，目前最有价值的可能就是我们的审美和判断力。
